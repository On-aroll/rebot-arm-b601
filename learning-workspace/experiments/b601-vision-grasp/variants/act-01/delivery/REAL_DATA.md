# 回板与实机数据回传

当前交付是仿真研究候选，默认仍为 V3。模型输出只是动作提议；本目录没有 CAN/ROS/电机 SDK 写入入口。板端架构、相机安装和可用算力尚未提供，因此本机 CPU 成本不能作为板端验收结果。

## 板上先做什么

1. 从交付包加载 `policy.pt` 或 `policy_cpu.ts`，先对 `example_observation.npz` 离线推理，对比包内 `example_action.json`。TorchScript 输入/输出已经标准化，归一化与相对动作还原规则在 `config.json`，Python 入口已经完成这些步骤。
2. 只接真实相机与只读反馈，测量连续 1000 帧的端到端 P50/P95/P99、RSS、CPU、温度和功耗，区分相机等待、预处理、模型、现有执行器。策略周期为 200ms，单次输出未来10步但只提议第一步；超时应由现有执行器按既有规则处理。
3. 先标定图像/深度配准、深度尺度、固定相机外参或腕部手眼、桌面/TCP，以及真实 J7 rad 与开口的查表。当前单指模型行程不是开口宽度，更不是 J7 电机角度。没有标定时不生成可执行的第七轴命令。
4. 现场运动只经现有唯一受保护执行器，保留当前限位、速度、力矩、所有权、新鲜度与恢复规则。模型不直接写电机增益、限流或零位。首阶段只做影子推理并记录提议，随后按现场验收流程逐步验证。

## 每次回传的 episode

把成功、失败、人工接管和未执行提议一起保留。推荐一个文件夹：

```text
episode-<UTC时间>-<设备ID>/
  manifest.json        设备/相机/固件/源码/模型/标定哈希、任务区域、单位与时钟说明
  calibration.json     K、深度尺度、T_base_camera_optical 或拍摄时的变换链、TCP、J7查表版本
  observations.npz     RGB uint8、配准深度float32米、图像时间戳、实际内外参
  trajectory.jsonl     单调时间戳、接收时间、q/qd rad、J7原始rad、已标定开口、图像索引
                       策略提议、执行器接受/拒绝及原因、实际下发命令和时间、控制来源
  events.jsonl         夹偏/抓空/滑落/接管/恢复/重试/观察或通信异常
  outcome.json         最终视觉验收与人工复核、失败原因、最多两次重试、现场录像引用
  SHA256SUMS           逐文件SHA256
```

时序必须是“当前已到达观测 -> 后续真正下发目标”。不要把编码器反馈当作 action，不要用提议替代被执行器拒绝的实际命令。保留相机时间、主机单调时间和接收时间，先估计时钟偏移，再按实际生效时间对齐；缺失或过期帧标记无效，不跨 episode 插值。

压缩后带回此仓库的 `variants/act-01/outputs/real-feedback/<设备ID>/<批次>/`，或上传同一**私有仓库**的 Release，再在训练主机下载并核验 SHA256。不要提交凭据，也不向公开数据集同步现场画面。当前实验原始 RGB-D/动作数据也在忽略的 `outputs/`，仅复制源码不会带走这些数据。

## 如何用于下一轮

- **先修仿真**：从空夹/不同开口建立 J7 查表与滞回；从已接受命令和反馈拟合分轴延迟、速度/加速度、跟踪误差、摩擦；从静态重复 RGB-D 测量深度尺度/噪声/缺失/遮挡。从抓稳与滑落实验估计接触参数范围，不用成功率倒推“更容易抓”的摩擦。
- **再修视觉**：在真实静态图上标注目标/遮挡与验收结果，检查当前红橙色立方体假设。更换形状、颜色或相机布局要新建数据版本。
- **再做模仿**：使用人工确认的正确动作与纠正段，保留失败但不要把失败指令作为正确动作标签。当前20维状态仅在 J7 完成标定后构造；仿真目标区域必须替换为现场标定区域。以设备/采集日期/完整 episode 划分训练、验证和最终测试，避免相邻帧泄漏。
- **独立验收**：冻结模型和阈值后，用另一批至少30个未见实机场景配对比较。记录完整任务、首次成功、抓空后恢复、误报、碰撞/保护拒绝、耗时及资源。现场结果决定是否采用；这轮仿真权重尚不具备实机采用资格。
