## 1. 范围与推荐结论

优先为照片中的 reBot B601 机械臂建立可交互仿真：显示模型 → 控制关节和夹爪 → 末端轨迹 → 桌面抓取。推荐 **Ubuntu 原生 + Pinocchio/Meshcat + MuJoCo**。ROS 2/MoveIt 2 在需要复杂避障或实机集成时加入；Isaac Sim/Isaac Lab 后置。

照片核查：第一张为电源，其铭牌型号可辨为 LRS-600-48；其余两张显示 reBot 品牌、银色结构与黄绿色饰件。外观与电源线索支持 B601-RS 的判断，但不是型号的最终证据。以机身铭牌或电机型号确认 RS/DM 后冻结配置。不能从两张不同视角的照片推断有两台机械臂。

默认首个交付是单臂模型、关节控制与末端轨迹。若需要兼容 DM，复用上层功能，单独验证 DM 的模型和控制参数；不将旧笔记中的“两台都要”当作本轮已确认要求。

## 3. 技术栈决策

| 组件 | 角色 | 实施优先级 |
| --- | --- | --- |
| 官方 reBotArm_control_py + URDF/网格 | 几何、关节定义、官方仿真示例 | 首期 |
| Pinocchio | 正运动学、雅可比、逆运动学求解和动力学计算基础 | 首期 |
| Meshcat | 浏览器查看模型、末端坐标和轨迹 | 首期；它本身不是接触物理引擎 |
| MuJoCo + Menagerie reBot 模型 | 重力、关节控制、碰撞、夹爪与物体接触 | 首期后半段 |
| ROS 2 Jazzy + MoveIt 2 | 规划场景、避障与标准化机器人接口 | 有明确需求再加入；先验证 reBot 包兼容性 |
| Gazebo | ROS 场景/传感器集成的可选后端 | 现阶段不与 MuJoCo 同时铺开 |
| Isaac Sim / Isaac Lab | 复杂视觉、合成数据和大规模训练的后续选项 | 后置，需重新评估硬件 |

核查依据：官方控制库的 `pyproject.toml` 明确要求 `>=3.10,<3.12`，`.python-version` 当前为 `3.10`。优先按仓库版本使用 Python 3.10；若固定版本的依赖验证通过，也可采用 3.11。不要直接用系统 3.12 强行安装。

Menagerie 的 `seeed_rebot_devarm` 明确使用 RobStride 执行器，因此是 RS 路线资产，不能当作 DM 的直接替代模型。它提供 MJCF、网格和场景，适合首个 RS 物理仿真。若最终确认是 DM，应先用官方 DM URDF 跑运动学，再单独审查或制作 DM MJCF。

NVIDIA 当前 latest 要求页列出的最低配置包含 32 GB 内存、RTX 4080 和 16 GB 显存。本机不满足该推荐路线的硬件门槛；旧笔记的 RTX 3070 / 8 GB 门槛不应继续当作当前版本要求。

6. 将来 ROS 2 保持其适配的系统 Python，和 reBot 环境通过进程/接口通信；不强迫所有生态共用一个 Python 环境。

首个可看的版本目标为 A+B，约 1–2 个工作日；到简单抓取约 4–8 个工作日。优先把模型、坐标与接触行为验证可靠，再考虑更复杂的应用。

建议验收指标（目标值，当前未实测）：

- 官方可达的测试位姿集：IK 的 FK 回代误差目标为位置 <1 mm、姿态 <1°；不可达目标明确返回失败。此处是数值一致性，不代表实机精度。
- Pinocchio/MuJoCo 使用同一来源几何、同一关节状态与同一末端坐标定义时，FK 对比目标同上；差异必须定位。
- 物理仿真连续运行 60 秒，无 NaN、求解器发散或非预期重置；记录关节跟踪误差和控制饱和情况。
- 在本机测量实时因子，简单场景目标 ≥1，显示目标 ≥30 FPS；首次测试再决定网格简化与渲染设置。
- 在声明的初始状态、控制器和摩擦参数下，固定种子重复 10 次抓取：目标成功 ≥9 次；物体抬离桌面至少 5 cm、保持 2 秒、再放置。随后改变初始位置验证泛化，不能用固定场景成绩代替泛化结论。

## 6. 必须处理的模型差异

1. **先确认型号。** RS/DM 的电机、惯量、零位和坐标定义分别管理。照片用于识别外观，不能用于推算精确惯量或关节标定。
2. **关节方向不能凭限位符号决定。** 当前 RS 的 J2/J3 范围为 0~3.14，DM 为 -3.14~0；六个旋转关节的局部 axis 符号也有差异。必须综合 joint origin、axis、零位与末端坐标验证映射，不能只给 J2/J3 乘 -1。不同几何的两型号也不应被要求同一 q 产生完全相同末端位置。
3. **夹爪统一对外使用开口宽度（米）。** 实机电机角、左右手指位移和总开口宽度分开定义；通过几何与标定得到换算，不照抄经验系数。平行夹爪作为一个控制量，正确处理两指耦合。
4. **关节限位不等于避碰。** 旧笔记记录了 DM 规格书和模型限位差异，本轮尚未重新逐页核读 PDF；实施时逐项确认。先统一坐标与零位，再在同一坐标下求约束交集，并预留可配置余量。限位本身不能保证不自碰，还必须检查连杆、桌面和物体碰撞。
5. **动力学需要独立验证。** 能打开模型不等于动力学准确。质量、惯量正定性、重心、执行器饱和、阻尼与摩擦分别核查。URDF 里的大速度数值不能直接当实机运行速度。
6. **末端定义明确。** 官方 RS 配置是 `gripper_end`，DM 是 `end_link`；项目再定义需要的工具中心点 TCP 偏置，用于 IK 与抓取目标。
7. **纯仿真与实机入口分开。** 首期只启动不访问 CAN/串口的仿真程序。以后增加读状态、镜像和控制时，再明确零位、通信协议及限幅；规划阶段不运行使能或电机运动命令。

推荐最小接口：`fk(q)`、`ik(target_pose)`、`set_joint_target(q)`、`set_gripper_width(width_m)`、`read_state()`。先实现单一型号的仿真后端，确有第二型号或实机需求时再抽象后端。

#### 拉取过程与两个坑（2026-10-06）

- **坑一：codeload 不支持 HTTP Range。** 它对本机代理始终返回 200 而非 206，且从字节 0 重发。按"追加续传"写下载器，会得到一个由多段重复内容拼接的文件——实测造出 133 MB 废料，内含 **55 个 gzip 文件头**，`gzip -t` 报 `invalid compressed data--format violated`。**判据：响应 `status != 206` 就绝不能追加。**
- **坑二：github / codeload 经本机代理被限速到 20–40 KB/s**，且与 502 交替出现。曾据此误判为"GitHub 整体不可达"，实际上是一直连通的，只是慢——该判断已在本次修正。
- **最终走法：** 文件清单取 GitHub API `git/trees/<sha>?recursive=1`（206 个 blob，`truncated=false`），文件内容经 **jsDelivr CDN** 逐文件取回，实测 **1603 KB/s**，全程 68 秒。脚本 `scripts/fetch_rebot_ros2_repo.py`。
- ⚠️ **完整性口径：jsDelivr 是第三方 CDN。** 本机无法连回 GitHub 逐文件校验，故 manifest 中记为 `verification: unverified-against-github`。今后 GitHub 可达时应重跑校验，不要把当前状态当作已核对。

ROS 2 本体安装见 `scripts/install_ros2_jazzy.sh`（默认 desktop 变体）。已知两个会阻断安装的坑已在该脚本内处理：官方 `packages.ros.org/ros.key` 为过期副本（2025-06-01 到期，需改从 keyserver 取同指纹更新副本），以及本机 MITM 代理导致该域名 https 证书校验失败（改用官方同样采用的 http:// 通道）。

当前仍未验证的事项：实机最终型号、显卡渲染链路、固定资产版本下的长时间仿真稳定性、抓取接触参数向真机迁移的可行性、ROS 2 下 reBot 包与当前 Python 3.10 环境的互操作方式。这些均非已完成能力。
