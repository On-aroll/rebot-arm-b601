### 根因分析（三条证据互相印证）

**证据一：CAN 侧是健康的。** `outputs/can_startup_verification.json` 记录接口 UP 时：

| 项 | 值 |
| --- | --- |
| 控制器状态 | `ERROR-ACTIVE`（CAN 的正常工作态，非 BUS-OFF） |
| `berr_counter` | `tx=0  rx=0` |
| `bus_error` / `bus_off` / `error_passive` / `arbitration_lost` | 全部 `0` |

**若接线、终端电阻或波特率有误，这些计数器必然上涨。它们是零。** 因此 CAN 物理层大概率是对的。

**证据二：USB 侧是坏的。** 内核日志 `usb_error_count_in_log: 470`，
最后一批为 15:48:30 连续 8 次：

```
peak_usb 3-3.4:1.0 can0: Rx urb aborted (-71)
```

`-71` = `EPROTO`。另外初始化阶段驱动的设置波特率命令 `f=0x1 n=0x2` 多次报 `-32`（`EPIPE`，端点被 stall）。

**证据三（关键推论）：`Rx urb aborted` 与总线上有无数据无关。**
驱动在接口 UP 时即提交接收 URB，不依赖 CAN 流量。出现该报错说明
**适配器没有响应 USB 的 IN 请求**。→ **只要这一条不消除，CAN 接线/终端电阻/波特率
怎么调都不可能收到帧。** 反过来，CAN 侧零错误正说明那些地方大概率本来就没问题。

### 设备身份问题（实测）

`lsusb` 依 VID/PID 数据库显示 PEAK PCAN-USB，但实际设备字符串是 **XCAN-USB**、
`bcdDevice=54ff`、序列号 `FFFFFFFF`。**即克隆品冒用 PEAK 的 VID/PID `0c72:000c`**，
内核 `peak_usb` 驱动按该 ID 匹配加载。初始化命令被 `-32` 拒绝，符合克隆固件
未完整实现 PCAN 协议的表现。**这是嫌疑，不是定论**——未证明固件不兼容。

### 第 4 步：适配器自环测试（独立于机械臂）

**前提：适配器插在电脑上，但 CAN 线不接机械臂**（这样总线上根本没有其他节点，
发送自测帧不可能影响电机）。此测试会发送数据，与前几步的纯只读性质不同，**属显式选择**：

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 1000000 loopback on
sudo ip link set can0 up
```

然后发送一帧并观察能否收回：

```bash
python3 - <<'PY'
import socket, struct, time
s = socket.socket(socket.PF_CAN, socket.SOCK_RAW, socket.CAN_RAW)
s.bind(('can0',)); s.settimeout(2)
frame = struct.pack('=IB3x8s', 0x7FF, 4, bytes([0xDE, 0xAD, 0xBE, 0xEF]))
try:
    s.send(frame)
except OSError as e:
    print('发送失败:', e); raise SystemExit(1)
try:
    print('收到回环帧:', s.recv(16).hex())
except socket.timeout:
    print('未收到回环帧 —— 适配器收发通道不可用')
PY
```

**判读**：
- 收到回环帧 → 适配器自身收发正常，问题在 USB 稳定性或 CAN 侧
- 未收到 → 适配器收发通道不可用，**与机械臂无关**，指向第 5 步

测试完恢复只监听：

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 1000000 listen-only on
sudo ip link set can0 up
```

### ⚠️ 重要：「收包 0」在这里**不是故障**

诊断结论显示"无数据"，但**不要把它当成问题**。原因：

**只监听模式下本机不发送任何请求，而 RobStride 这类 CAN 伺服电机不会主动广播状态。**
没有请求就没有应答，零帧是**预期行为**。

换句话说：**"握手"这件事在纯只读模式下不可能完成**——握手本身就需要发出请求。
要往下走，必须做一次发送，这是显式选择，不是默认动作。

### 下一步：先做被动电气检查，再做握手

**A. 被动电气检查（不发任何帧，先做这个）**

| 检查 | 方法 | 预期 |
| --- | --- | --- |
| 终端电阻 | **全部断电**，万用表测适配器端 CAN_H ↔ CAN_L | **约 60Ω**（两个 120Ω 并联）。读 120Ω = 少一个终端电阻；开路 = 断线；接近 0Ω = 短路 |
| 通断 | 断电，量适配器到机械臂接插件的 CAN_H / CAN_L 通断 | 导通 |
| 共地 | 量适配器 GND 与机械臂 GND 之间电阻 | 接近 0Ω |

这三项不需要 sudo、不改变任何配置、不发送任何帧，却能排掉大部分接线问题。

**B. 电机握手（需要发送，显式选择）**

```bash
# 1) 退出只监听模式（需要终端密码）
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 1000000 listen-only off   # ← 必须显式 off
sudo ip link set can0 up

# 2) 只 ping，不使能、不运动
rebot-can-ping                      # 默认 ping ID 1..7
rebot-can-ping --ids 1              # 只 ping ID 1
rebot-can-ping --model rs-00 --ids 4,5,6,7
rebot-can-ping --check-only         # 只检查环境，不发帧
```

> ⚠️ **`listen-only` 不会因为只写 `bitrate` 而被清除。**（2026-10-07 实测踩到）
> SocketCAN 的 `ctrlmode` 只有**显式指定**才会改变。执行
> `ip link set can0 type can bitrate 1000000` 之后，`bitrate` 确实变成了 1000000，
> 但 `ctrlmode` 仍然是 `['LISTEN-ONLY']`，发送照旧被拒。
> 必须写全 `bitrate 1000000 listen-only off`，且改 ctrlmode 前接口要处于 `down`。
>
> 自查一条命令即可确认：
> ```bash
> ip -details link show can0 | head -3     # 看 can <...> 里还有没有 LISTEN-ONLY
> ```

`scripts/rebot_can_ping.py` 只调用 `robstride_ping()`（C 库的真实握手，返回
`device_id` / `responder_id`），**不使能、不发运动指令、退出时也不调用 `disable_all()`**。

> **为什么不用官方 `example/0x01rs06_test.py`**：它虽是官方示例，但

## 16:15 首次握手尝试：ID 1 超时，但**总线计数器给出强线索**

用户清掉 `LISTEN-ONLY` 后执行 `rebot-can-ping --ids 1`：

```
接口 can0 已就绪：ERROR-ACTIVE  bitrate=1000000  ctrlmode=None
目标电机 ID: [1]   型号: rs-06   host_id: 0xFD
ID 1   无应答  (robstride_ping failed: ping 1 timed out)
```

**发送后的总线计数器（关键）：**

| 项 | 值 |
| --- | --- |
| `tx.packets` | **3**（发出了 3 帧） |
| `tx.errors` | 0 |
| `berr_counter` | `tx=0  rx=0` |
| `bus_error` / `bus_off` / `error_passive` / `error_warning` | 全 **0** |
| `rx.packets` | 0 |

**推断（强，但非定论）：帧被应答了。**

CAN 协议规定：发送方在 ACK 位期待至少一个接收方拉低电平。**若总线上没有任何节点
应答，发送方必然报 ACK 错误**，TEC 上涨并自动重发，累积后进 error-passive / bus-off。
而这里是"发了 3 帧、错误计数全零"。

**关键区分：应答发生在数据链路层，与帧 ID 是否匹配无关。** 即使 ID 不对，
对方照样 ACK，只是不会回话。**所以"无应答"与"无人 ACK"是两回事。**

若上述推断成立，则：接线正确、CAN_H/CAN_L 未接反、波特率一致、机械臂确实在通信
——**问题在协议层（ID 或请求格式），不在电气层。**

### ⚠️ 必须做的对照实验：验证计数器是否可信

**上述推断有一个前提：这个克隆适配器会如实上报总线错误。** 若它不上报，
则"错误计数为零"不能推出"被应答"。**验证方法：**

```bash
# 1) 把 CAN 线从机械臂上拔掉（适配器留在电脑上），保持接口 up
# 2) 再 ping 一次
rebot-can-ping --ids 1
# 3) 看总线计数变化
```

| 结果 | 含义 |
| --- | --- |
| 拔掉后出现总线错误 / TEC 上涨 | **计数器可信** → 之前的零错误确实意味着"被应答"，方向转向协议层 |
| 拔掉后仍然零错误 | **计数器不可信**（克隆固件不上报）→ 之前的推断作废，需另找判据 |

脚本已内置该对比：每次 ping 都会打印前后的 `tx_packets` / `TEC` / `bus_error` 变化，
并给出「被应答 / 未被应答 / 未发送」的判读。报告写入 `outputs/can_ping.json`。

### 并行的被动检查：终端电阻 —— ✅ 已做，结果 60Ω

用户**全部断电**后测量适配器端 `CAN_H ↔ CAN_L` = **约 60Ω**。

**这是决定性的正面结果。** 两个 120Ω 终端电阻并联才等于 60Ω：

- 线路**通**（不是开路）
- 两端终端电阻**都在**（不是只接了一端）
- 适配器**确实电气连到了机械臂的总线**上

→ **物理层（线缆、接插件、终端）至此可以判定为正常。**

配合前面"发出 3 帧、总线错误全零"，两条独立证据方向一致。

> 补充可做的确认：把 CAN 线从机械臂拔掉后再量一次。若读数变成约 120Ω，
> 说明 60Ω 里有一个来自机械臂端 —— 进一步坐实机械臂那一端是接上的。

### 对照实验：❌ 推翻了"帧被应答"的推断

第一次执行时接口处于 DOWN（`result: blocked`），重跑后拿到结果：

**CAN 线从机械臂拔掉、总线上没有任何节点的情况下：**

```
发送帧数 3   接收帧数 0
TEC 0 → 0   bus_error 0 → 0
```

**拔掉线仍然是零总线错误。** 若计数器可信，此时必然出现 ACK 错误、TEC 上涨。

### 结论：本适配器不上报总线错误，计数器不可信

**因此前面「发出 3 帧且零总线错误 ⇒ 帧被应答」的推断作废，予以撤回。**
零错误既可能意味着"被应答"，也可能意味着"根本没上报"——**用这组计数器区分不了**。

这正是对照实验的价值：它没有"确认"推断，而是**否证**了它。
若跳过这一步，就会带着错误结论一路往下查协议层。

**教训**：用某个观测指标下结论之前，先验证**这个指标本身会随条件变化**。
否则"读数不变"会被误读成"情况正常"。

### 仍然成立的结论

| 结论 | 依据 | 是否仍有效 |
| --- | --- | --- |
| USB 层正常 | 直连后 470 条 USB 错误归零 | ✅ 有效 |
| CAN 控制器可启动 | `UP` / `ERROR-ACTIVE` / 1 Mbps | ✅ 有效 |
| **物理层接线正常** | **万用表实测 60Ω** | ✅ 有效（**独立于任何软件判断**） |
| 帧被应答 / 总线上有活节点 | 零总线错误 | ❌ **已撤回** |

**现在能确证的只剩万用表那一项。** 这也说明为什么被动电气测量不可替代——
它不依赖适配器固件是否如实上报。

### 下一步：用万用表判断"机械臂的 CAN 到底活没活"

既然适配器的错误计数不可信，就改用**不依赖固件的物理测量**。

**⚠️ 这一步要在机械臂通电状态下做**（与测终端电阻时的断电状态不同）。

| 测量 | 位置 | 预期读数 | 含义 |
| --- | --- | --- | --- |
| CAN_H ↔ GND | 适配器端或机械臂端 | **约 2.5 V** | 总线处于隐性（空闲）电平，收发器已上电 |
| CAN_L ↔ GND | 同上 | **约 2.5 V** | 同上 |
| CAN_H ↔ CAN_L | 同上 | 约 0 V | 空闲时差分接近零 |

**判读：**

- **两端都是约 2.5 V** → 机械臂的 CAN 收发器已上电并在空闲态，
  说明机械臂确实在总线上 → 方向转向**电机 ID / 请求协议**
- **两端都接近 0 V** → 机械臂那侧的收发器没有供电/未激活，
  或线路根本没连到它 → 先解决机械臂供电与 CAN 使能
- **一端 2.5 V 一端 0 V，或读数异常** → 线路问题（接插件、断线）

这项测量**不需要 sudo、不需要发帧、不依赖适配器固件**，
是当前唯一能把"机械臂侧是否在线"独立判出来的手段。

## ⚠️ 更正：CAN_H/CAN_L 的 2.5V 不能证明机械臂在线

**前面据"CAN_H/CAN_L 约 2.5V"推断"机械臂收发器已上电并在总线上"，这个推断有误。**

**一个通电的 CAN 收发器在隐性（空闲）状态下，自身就会把总线偏置到约 2.5V**
——不需要总线上存在其他节点。也就是说，**只插着适配器也能测到 2.5V**，
那次测量不具备区分能力。

**正确的测法**（唯一能区分的方式）：

1. **把适配器的 USB 拔掉**（让适配器断电）
2. CAN 线仍接在机械臂上，**机械臂保持通电**
3. 在适配器接插件处量 CAN_H / CAN_L 对 GND

| 读数 | 含义 |
| --- | --- |
| 约 2.5 V | **是机械臂在驱动总线** → 机械臂侧收发器已上电 |
| 接近 0 V | 机械臂侧收发器未供电/未激活 |

**教训**：一个观测值只有在"条件变化时它也会变"的前提下才有诊断力。
2.5V 这个读数在两种情况下都会出现，因此推不出任何结论。

| 帧**未被 ACK** | 控制器不断重传 → 队列填满 → **ENOBUFS (errno 105)** |

### 实测对照（同一接口、同一模式）

| 发送速率 | 结果 |
| --- | --- |
| **1 Hz 慢发 5 帧** | **5/5 全部成功** |
| **500 Hz 快发** | **第 16 帧失败**（0.03 秒内） |
| 500 Hz 快发（第二次，200 帧上限） | **第 22 帧失败**（0.048 秒，≈458 帧/秒） |

### ⚠️ 但这个判据不是定论 —— 必须先做对照实验

**保留意见**：458 帧/秒仅占 CAN 1 Mbps 理论上限（约 7700 帧/秒）的 **6.5%**。
队列在这么低的速率就满，**也可能是这个克隆适配器自身的吞吐上限**，
而不一定是"没有 ACK"。**仅凭单次测量无法区分。**

**对照实验（下一步）**：把 CAN 线从机械臂拔掉，用**完全相同的参数**再跑一次：

| --- | --- |

| 失败位置**基本相同** | 这个判据测的是适配器吞吐，**与 ACK 无关 → 判据失效** |

### 新增：发送期间电压探测工具

`scripts/rebot_can_tx_probe.py`（软链 `rebot-can-txprobe`）。

**要解决的问题**：自环测试通过只证明适配器**内部**通道可用
（自环在控制器内部完成，**不经外部收发器与线缆**）。因此

**原理**：持续发送时总线大量处于显性电平，万用表读平均值会看到偏移：

| 状态 | CAN_H 对地 | CAN_L 对地 |
| --- | --- | --- |
| 空闲（隐性） | 约 2.5 V | 约 2.5 V |
| 持续发送 | **升高**（趋向 3.5 V） | **降低**（趋向 1.5 V） |

**读数纹丝不动 ⇒ (b)，问题在适配器或接线；有明显偏移 ⇒ (a)，问题在机械臂侧。**

```bash
# 切普通模式
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 1000000 loopback off listen-only off
sudo ip link set can0 up

# 持续发送 30 秒，期间用万用表量 CAN_H / CAN_L 对地
rebot-can-txprobe --seconds 30
```

工具自带前置检查：ctrlmode 含 LOOPBACK/LISTEN-ONLY 时直接拒绝（那两种模式下
帧不上总线，测了没意义）。发送结束后会报告接口 state，
**若变成 BUS-OFF，说明控制器确实检测到发送失败 → 收发器在驱动总线，是对侧没应答。**

⚠️ 会持续向总线发送保留 ID 的帧（`0x7FE`），电机不会识别，但请确保机械臂处于安全状态。

- 官方 `example/` 下另有 `0x01damiao_test.py`

**核对方法**：看电机外壳上的型号标识；或看机械臂铭牌/包装。
**同时可直接试**：`motorbridge-cli scan --vendor all`（会依次尝试
damiao / myactuator / robstride / hightorque 四种协议）。

#### ② 用更正后的方法测机械臂侧是否在驱动总线

**CAN 线从适配器上拔下**（让适配器不参与），**机械臂保持通电**，
在**机械臂的 CAN 接插件处**量 CAN_H / CAN_L 对 GND：

| 读数 | 含义 |
| --- | --- |
| 约 2.5 V | 机械臂侧收发器已上电，在驱动总线 |
| 接近 0 V | 机械臂侧收发器未供电 / 未激活 |

这次测量有区分力，因为适配器已从总线断开。

### 🔑 找到覆盖缺口：host_id 只试了一个

读 motorbridge 的 `cli/scan.py` 发现，**官方 scan 会依次尝试多个 host_id**：

```
--feedback-ids  默认 "0xFD,0xFF,0xFE,0x00,0xAA"
```

而 `scripts/rebot_can_ping.py` **只用了 0xFD 一个**。

**若电机期望的 host_id（主机/主站 ID）不是 0xFD，ping 就永远不会被响应**
——这与电机 ID 是否正确无关，是主机侧的标识不匹配。

> 注意 `--feedback-ids` 是**主机侧 ID 候选**，不是电机 ID。

### 改用官方 CLI 扫描（同样只查询，不使能、不运动）

`motorbridge-cli` 已随 motorbridge 装好。新增包装脚本 `scripts/rebot_can_scan.sh`
（软链 `rebot-can-scan`），已内置 host_id 候选与接口前置检查：

```bash
rebot-can-scan              # 默认 rs-06，ID 1..16
rebot-can-scan rs-00        # 按 rs-00 扫描
rebot-can-scan rs-06 1 32   # 指定型号与 ID 范围
```

等价的手动命令：

```bash
~/.local/share/robotics/envs/rebot-sim/bin/motorbridge-cli scan \
  --vendor robstride --channel can0 \
  --start-id 1 --end-id 16 \
  --feedback-ids 0xFD,0xFF,0xFE,0x00,0xAA \
  --timeout-ms 80
```

**官方 scan 的安全性**：读其 `_scan_robstride()` 实现，只调用 `robstride_ping_host_id()`
与 `robstride_get_param_f32_host_id()` 作为回退，**不使能、不发运动指令、不改参数**。
与本项目"只读优先"的立场一致。

### 顺带确认：60Ω 是在哪种状态下量的

需要用户补充说明：测 60Ω 时 CAN 线是**接着机械臂**还是**已经拔掉**？

- 接着机械臂量的 60Ω → 两个终端电阻都在（含机械臂那端）→ 接线确实通到机械臂
- 拔掉后量的 60Ω → 说明两个电阻都在适配器侧，**不能推出线路通到机械臂**

**建议两种状态各量一次：** 接着约 60Ω、拔掉约 120Ω，才构成完整的接线证据链。

### 下一步顺序

1. **拔掉 CAN 线 ping 一次**（对照实验）—— 判定计数器是否可信
2. **断电量终端电阻** —— 独立验证接线
3. 若 1 判定"被应答" → **扩大 ID 扫描**：`rebot-can-ping --ids 1,2,3,4,5,6,7`
   （官方 ID 1–7 只是参考配置，未与本台核对）
4. 若 ID 扫完仍无应答 → 说明该 ping 协议不被本台电机接受，
   需要改用官方文档里的具体请求帧，或核对电机固件版本
