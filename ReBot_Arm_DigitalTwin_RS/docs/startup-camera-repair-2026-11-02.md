# 启动、过期恢复提示与相机采集修复

用户报告：重新打开项目后控制台仍无法使用，恢复状态似乎修复不了，相机也突然无法连接；现场接线无异常。

## 已定位的问题

1. 实时状态实际为 READONLY/IDLE，六轴模式0、无控制权、未准备、无目标或参考、恢复锁已清，但顶层 `message` 仍保留“上次停止/参数恢复未确认”。`TwinControl.tick` 只在硬件有错误时覆盖文字，没有同步异步重置完成的消息。新离线用例在旧码复现失败，修复后通过。
2. 桌面启动器只打开网页，仍要手动完成四步；网页后台重载还会将 ROS 环境检查状态变回“待检查”。新增一键启动作业，启动过程和复用结果都在启动台显示，避免将“网页已开”当作“整套后台已准备好”。
3. Gemini USB 设备及稳定 by-id 路径存在，但采集进程已不在运行。原 `/camera/color/preview/compressed` 还依赖先前手动运行的颜色检测节点，项目退出后没有自动恢复。

## 最终行为

- 桌面启动器现在运行 `quick_start.sh --hardware`：启动网页后发起一键检查，按 ROS → ROSBridge → CAN → 唯一只读实机驱动 → 相机顺序执行。已就绪的服务直接复用；不会使能、回零或运动。默认仿真命令及 `--web-only` 保留原语义。
- 启动台增加“一键检查并启动实机与相机”和独立的相机状态、日志、重试入口。反馈可读与恢复锁分开显示，真实恢复锁仍提示“需恢复”。相机不在时给出提示，不阻止只读观察机械臂。
- Gemini 采集使用系统 Python/OpenCV，独立于控制环境的 NumPy 2。通过稳定 by-id 选择颜色接口，发布原彩色流和320×240 JPEG预览；配置8Hz，不依赖红黄蓝检测程序。相机采集由独占锁防止重复启动。
- 用户在相机页面明确点击“连接画面”时，会检查并启动采集后台，再连接只读图像通道。普通页面自动订阅只观察画面，不启动机械臂。
- “重置与维护”在原有硬件恢复通过后也会检查并恢复相机；缺失快照、未知参数等硬件保护照常保留。相机失败会单独显示原因。
- 完成重置的消息按任务编号和状态同步一次，不覆盖之后的新提示；新故障仍优先显示。网页收到真正清除恢复锁且核对成功的状态后，也清除旧的失败文字。
- 结束项目现在包含相机采集和以前的颜色检测进程。正常结束相机不再将 `ExternalShutdownException` 记录成未处理异常。
