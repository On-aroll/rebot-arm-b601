# 桌面启动台 CAN 与实机反馈修复

2026-11-02，北京时间。

## 原因

桌面 `.desktop` 正确启动 `quick_start.sh --web-only`，网页和 ROSBridge 都正常。10 月 31 日主机重启后，10 月 30 日临时设置的接口名失效：Jetson 板载 mttcan 恢复成 `can0`，PEAK USB-CAN 则为 `can1`。旧准备脚本只检查 `can0`，因此把没有接机械臂的板载接口配置为 1 Mbps；该接口随后进入 BUS-OFF，真正的 USB 接口仍 DOWN。

实机驱动同样固定连接 `can0`，读取 `0x7019` 超时后退出。硬件启动器没有把子进程退出状态交给启动台，网页继续等满 30 秒后才给出通用超时提示。

## 修复

- `scripts/can_interface.py` 通过内核驱动身份识别 PEAK USB-CAN。启动台状态检查、CAN 准备和实机驱动入口共用这份检查，避免仅按接口名认错设备。
- 保留原执行器仅使用 `can0` 的审计约束。点击启用 CAN 时，只有唯一 PEAK 适配器处于 DOWN、没有 CAN 接收者、没有所有权锁持有者，才把空闲板载接口移至 `can_native0`、USB 移至 `can0` 并配置 1 Mbps。本次板载接口已 BUS-OFF，允许关闭后改名；健康活动的板载接口、活动 USB、多适配器、名称冲突均拒绝自动修改。
- USB 自身 BUS-OFF 不自动复位。配置只更改主机网络接口，不发送电机命令；整组配置合并为一次管理员认证，没有安装免密规则。
- `hardware-launcher.js` 把实际子进程退出和本次启动日志尾部交给启动台，启动失败可及时显示具体原因。原唯一控制器、恢复锁和使能/运动条件不变。

## 本机验证

- 7 项 Python CAN 识别/配置门槛测试、11 项 Node 启动器/启动台测试通过；包含真实隔离失败子进程和提前退出反馈测试。语法和 diff 检查通过。
- 本轮确认无实机驱动、CAN 接收者后完成改名。PEAK `can0` 已 UP / 1 Mbps / ERROR-ACTIVE，收发正常且错误计数 0；板载 `can_native0` 保持 DOWN。
- 仅重载空闲网页服务以加载新后端，保留既有 ROSBridge。随后通过原启动台管理接口启动唯一 CSP 只读驱动，约 5 秒后就绪；未调用使能、准备、接管、运动或参数恢复。
- 连续 40 帧有效 READONLY/IDLE，无 owner/prepared/goal/reference/recovery，最大反馈年龄 115.245 ms；同一观察窗口 command/reference 各 0。J7 未探测、未授权、未激活。
- 217 份既有硬件 JSON 前后清单与 SHA-256 完全一致，没有新增硬件会话报告。
- 页面已实测显示 **4 / 4 步就绪** 和 **实机反馈有效 · READONLY**。证据及截图保存在忽略目录 `outputs/startup-repair-20261102/`。
