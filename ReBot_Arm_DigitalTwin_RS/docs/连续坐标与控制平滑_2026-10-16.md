# 连续坐标与控制平滑：第一批改进

日期：2026-10-16。适用：3002 网页的六轴 CSP 统一控制入口。

本批处理需求第 1、3 项。代码和离线检查已完成，真实运动手感尚待现场验收。
其余需求的状态、依赖和接口约定见[需求与扩展实施清单](需求与扩展实施清单_2026-10-16.md)。

## 1. 为什么第二个相近坐标也会失败

空间坐标接近，并不保证关节姿态或关节之间的运动路径接近。特别是“仅位置”模式，
同一 XYZ 可以有多个腕部、肘部姿态。此次也发现了两个软件衔接问题：

- 已经使能的第二条轨迹，以带跟随误差的编码器值重新规划，却又套用首次使能的 0.1° 起点对齐检查，容易误拒绝。
- 仅位置逆解没有对原姿态的轻微偏好，近邻目标可能选择变化较大的关节解；第一组解的路径失败后，没有检查其它候选。

现在：

1. 已启动的会话从后台最后发送的保持参考规划，另外保存实际反馈；执行前仍独立检查反馈是否发生变化。
2. 首次使能仍从新鲜实际编码器位置预装载，并保留原起点检查。
3. 逆解加入轻微种子姿态偏好，优先保持关节解连续；位置、姿态误差容限保持原值。
4. 有限时间内检查多个逆解候选；各候选经过相同的限位、自碰撞与模型重力路径检查。
5. 几何上有解、但候选路径均不通过时，返回 `PATH_REJECTED`，明确展示路径拒绝原因。

这属于有限候选筛选，还不是能绕开障碍物的全局路径规划器。真实越界、碰撞或朝向约束导致的不可达仍会拒绝。
旧日志没有记录每次预览拒绝详情，因此以上是代码确认的问题，不能倒推每次现场失败都由它们造成。

## 2. 运动为什么会一顿一顿

最近实机日志中，目标更新的中位间隔约 91–92 ms，个别间隔达到 256–282 ms。
原先在一整轮同步 SDK 查询结束后才发下一组位置目标，容易形成阶梯。
其中一次会话因已使能轴超过 300 ms 命令有效期停止；其它记录含主动停止和 ROS 断开，不能统一解释成负载不足。

本批改为：

- 坐标运动：ROS 刷新同一条解析五次曲线，唯一 CAN 工作线程在参数回复间隙，按当前单调时间采样曲线。
- 完整模式：参考目标周期为 20 ms；同步 SDK 阻塞仍会增加实际间隔，页面分别显示目标周期、运动实测周期和反馈查询耗时。
- 键盘与手柄：保留已有死区、非线性杆量响应与共用渐进加减速；后台最多外推一帧、50 ms 的已知关节速度，减少 20 Hz 输入之间的台阶。
- 松安全键、保持、输入过期、停止时清空曲线和速度预测；延迟恢复后不补走旧输入。
- 跟踪误差按“这次位置查询发起时已经发送的参考”比较，避免把旧反馈与未来目标比较而误报；新鲜反馈真正卡住时仍触发原 3° 检查。
- 六轴目标速度预算使用同一组发送时刻，避免六次串行写入耗时造成临界速度误报。

没有增加 CAN 所有者或线程。位置反馈仍约一轮 85 ms，不能把 20 ms 参考目标周期写成反馈频率，
也不能宣称实现了官方另一套 MIT 链路的 125 Hz 硬实时控制。

## 4. 参数与诊断

采用上一批[官方参数对齐](官方参数对齐_2026-10-16.md)的包络。
本批没有修改设备原限速、力矩/电流上限、零位、PID、flash、关节名义限位和反馈/命令/心跳时限。
坐标时长继续按速度、4 rad/s² 加速度和 30 rad/s³ jerk 上限计算；本批未为手动控制增加新的 jerk 保证。

失败的控制请求新增记录在 `outputs/twin-console/hardware/control-rejections.jsonl`，
包括操作、目标、实际关节、参考关节和拒绝诊断，不记录租约 token。
日志写入或无效数值序列化失败不会影响控制停止；相关错误返回仍照常发布。
主运动报告仍保留原始输出、反馈、停止和参数恢复证据。
