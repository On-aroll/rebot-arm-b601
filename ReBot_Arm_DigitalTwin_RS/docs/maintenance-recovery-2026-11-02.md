# 从“重置与维护”恢复连接与状态

用户明确要求：今后主动执行恢复操作时，默认其已经确认现场状态，不再另问一次。本轮将此约定落实到具体按钮，而不是把打开维护页面当作操作授权。

## 使用

先可靠支撑机械臂，检查供电和 USB-CAN 接线，再打开“重置与维护”，点击 **“已支撑，恢复连接与状态”**。这次点击就是本次现场确认，允许失能撤力，以及必要的故障驱动退出和只读重连。无需再次勾选现场确认或对话确认；系统权限认证窗口仍由操作系统决定。

- 通信正常：复用当前唯一驱动，通过原有 `/rebotarm/twin/reset` 清除旧输入、失能、停稳核对及参数恢复。
- 断线或驱动故障：核对项目进程身份后正常退出旧驱动，确认已退出，检查 ROS、联动接口及 USB-CAN，再启动唯一只读驱动并执行原有恢复。
- 完成：必须看到对应重置任务成功、有效反馈、READONLY/IDLE、六轴模式0、无 owner/准备/目标/参考/恢复锁、夹爪未活动且未授权。随后由用户重新选择控制范围、准备和使能。
- 失败：显示具体原因，保留原始恢复记录及锁定。断电、线缆未接、USB 自身 BUS-OFF、未知参数或原始快照缺失，不会被标记为恢复成功。

恢复不使能、不回零、不重放程序或历史目标，不修改零位、PID 或保护限值。恢复本身可能按原始快照恢复本会话临时运行参数，仍只经已有唯一 CAN 线程执行，不增加 CAN 写入者。

## 实现与验证

后端 `/api/maintenance/restore` 要求本机同源 POST 和明确的 `confirmed:true`。操作确认与进度保存到忽略的 `outputs/maintenance/<任务编号>.json`，初始确认记录保存失败时不会开始操作。重复点击合并同一任务；维护进行时拒绝并发的启动/退出等 HTTP 写操作。驱动退出仍按 PID、出生标记核对，绝不强杀实机驱动。多份驱动、身份改变或无法退出时停止后续处理。

前端只在点击恢复按钮时发送确认；重载页面仅查询已有任务，不发起新恢复。浏览器清空本页控制权、按键、旧目标及旧运动许可，恢复完成后只连接反馈。仿真仍使用原有仿真重置流程。

离线测试覆盖确认语义、断线与健康驱动两条流程、重复点击、身份变化、并发任务、记录写入失败、快照缺失、状态先于服务响应到达、结果编号匹配、失联和最终失能门槛；包含实际网页控制器及隔离 HTTP 服务测试。没有为测试执行实机重置、使能、运动或 CAN 重配。
