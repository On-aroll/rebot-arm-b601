# Ruckig 共用运动方案 · 2026-10-17

## 使用

工作台 `http://127.0.0.1:3002/` → **控制算法 → 共用运动方案**。

- 默认 **Ruckig · 连续S曲线**。在六轴完整控制下，坐标到点、键盘、手柄、TCP拖拽、程序和外部位置/速度算法使用这一参考生成器。
- **原方案**保留五次到点曲线与手动加速度平滑，可在未准备、未接管的只读状态选择作对比。切换不会使能或运动，会清除旧路径检查、预览和算法试算；后端拒绝在运动/保持/恢复中切换。
- 小幅试机及 J7 夹爪保留既有曲线；J7 仍在键盘和手柄中操作，仍共用唯一 CAN 所有者。
- 导入程序不会启动，点击「使能并执行程序」才走既有执行流程；仿真仍可选。程序仍按步骤到位停稳，未实现无停顿穿点。

## 实际修改

1. 新增纯数学模块 `twin_motion.py`，锁定 `ruckig==0.12.2`（本机 Python 3.12 可用官方二进制 wheel）。六轴速度、加速度、jerk 约束使用既有官方与设备限制，不提高电机原限速、不改 PID、零位或 flash。
2. 到点曲线采用一个标量进度驱动六轴，严格沿着已检查的关节空间线段，避免逐轴独立重定时改变路径。端点速度、加速度为零；保留程序各步 speed 和最低时长要求。
3. 手动及算法速度输入在 CAN 所有者中生成 Ruckig 参考，不在 ROS 和 CAN 两处重复平滑。仿真使用同一个数学实现。TCP拖拽仍通过共用手动执行器。
4. 每次从已发送参考推进。正常回中允许受约束减速；松控制键、暂停、输入过期、通信保持清空旧速度和加速度，不恢复旧轨迹。限位前用包含当前加速度的完整制动曲线检查停止范围。
5. 到点轨迹的 CAN 时间按实际机会推进，延迟一次最多计入50ms；同一轨迹的 ROS 刷新不会将时间清零。ROS 跟踪检查对照实际已发参考，底层3°保护仍保留。
6. 回归发现计算被调度延迟后会压缩下一组目标的间隔：原调度以计算前时间推进下一周期。现以成功发送组的真实起始时间计算速度预算，并按整组完成时间跳过错过的20ms槽位，避免补发。加入80ms计算阻塞的内存SDK回归。
7. 网页显示控制器确认的当前方案，阻止切换未确认时接管/执行。页面缓存 v138-ruckig，三个修改脚本均更新查询版本。

500ms命令期限沿用完整 v4；反馈600ms、网页500ms、心跳700ms、手动输入250ms及既有跟踪/电流/力矩/路径保护不变。20ms是参考调度目标，不是硬实时保证。计算错误在已激活完整控制中进入既有通信保持流程；硬故障、明确失能等仍按原规则处理。

## 范围

当前驱动后端仍是 CSP 原生位置控制；外部算法是受约束的位置/速度参考接口。MIT力矩/阻抗、重力前馈尚未接通，不在界面伪装成可选驱动。此次未新增实机使能或运动，现场连续运动是否仍颤动尚未验收。
